# Layer 5 part A: SIEM and detection

*Notes file of the part A session (branch `layer5/part-a-siem`, package `dev.dwarpal.siem`). Read [layer-5-plan.md](../layer-5-plan.md) first; keep this file up to date.*

## What was built

| Class | What it does |
|---|---|
| `EncryptedAuditStore` | The audit trail at rest. Implements `AuditSink` and `AuditSource`. One append-only file: a header (`DWAS`, version, 16 random bytes of store id) and one frame per record, each sealed on its own with AES-256-GCM (JDK provider), a fresh random 96-bit nonce, and `"dwarpal/siem/store/v1" ‖ storeId ‖ sequence` as associated data. Accepts only the next record of the chain (sequence + 1, linked to the previous MAC). Records at most 1 MiB, frames bounds-checked before any allocation, batches capped at `MAX_BATCH`. Damage (failed tag, torn or oversized frame, broken link) is found on open and on every read; the good records before it stay readable, reading past it throws, writes are refused. A file lock refuses a second writer. Durability is `SYNC_EVERY_RECORD` (fsync per record, the default for production) or `OS_BUFFERED` |
| `HeadAnchor` | Writes the chain head (sequence, MAC) to a separate file, on demand (`anchor`) and on a schedule (`schedule`, failures counted, the schedule survives them). The line is `dwarpal-anchor/v1 seq mac writtenAt hmac`, HMAC-SHA256 under its own anchor key, replaced atomically (fresh temporary file with `CREATE_NEW`, then an atomic move). Only moves forward (rollback and rewrite refused); a missing file after one existed is tampering; every write renews the time, and `readFresh(maxAge)` refuses a stale anchor (R-A1) |
| `Exporters` | Audit events and alerts as JSON lines (lossless), ArcSight CEF and RFC 5424 syslog. Names and values are escaped by each format's rules (see design decision 4) so one field cannot forge another field or another event |
| `DetectionEngine` | Reads the trail through a keyed `AuditCursor` it builds itself (so detection never runs on unproven records), runs the rules, raises `Alert`s. Deduplication, throttling, bounded state, back-pressure towards the sink, and fail-closed handling of the trail itself (one CRITICAL alert, then stop). `resume` from a checkpoint; `flush` closes open windows; `stats` for monitoring the monitor |
| `Rules`, `WindowCounter` (package-private) | The standard rules and the bounded sliding-window counter they share |

### Rules

Thresholds are starting values for a small organisation. They are **assumptions, not measured rates**; part C's calibration can replace them.

| Rule id | Fires on | Severity | Dedup key |
|---|---|---|---|
| `break-glass-used` | every `BREAK_GLASS_USED` | CRITICAL | grant id |
| `honeytoken-touched` | `ACCESS_DECISION` with policy `hard-gate:honeytoken` | CRITICAL | subject + device |
| `stolen-token-revoked` | `SESSION_REVOKED` whose reason is the PA's "possible token theft" (token presented for another subject or device) | HIGH | session id |
| `deny-storm-subject` | 5 DENY for one person in 15 min. Names the person as the **target** plus the addresses; the summary says it is not evidence against them | MEDIUM | subject |
| `deny-storm-ip` | one address denied 10 times, or for 5 different people, within 1 h (stuffing, spray, Tor) | HIGH | address |
| `mfa-fatigue` | 5 STEP_UP for one person within 30 min with no ALLOW in between (M9: every prompt is another chance a tired user approves) | HIGH | subject |
| `impossible-travel-allow` | a decision with a positive `impossible-travel` factor, then an ALLOW for the same person within 2 h (or the flagged decision itself allowed) | HIGH | subject + flagged record |
| `dlp-block-spike` | 5 `casb.dlp` BLOCK records for one person within 1 h | MEDIUM | subject |
| `pam-refused` | 3 `ELEVATION_REFUSED` / `ELEVATION_APPROVAL_REFUSED` for one person within 1 h (PAM throttles its own refusal records, so this is a lower bound) | MEDIUM | subject |
| `break-glass-refused` | every `BREAK_GLASS_REFUSED` | HIGH | account |
| `audit-chain-break` | the cursor finds a gap, reordering, bad link, bad MAC or unreadable payload, or the source throws (for example a damaged store) | CRITICAL | once, then detection stops |
| `audit-anchor-mismatch` | the trail stops short of the anchor (truncated), disagrees with it (rewritten), or the anchor is unusable (forged, rolled back, removed, stale) | CRITICAL | once, then detection stops |
| `alert-flood` | a rule went over its hourly cap | HIGH (CRITICAL for a CRITICAL rule) | rule + hour |
| `detection-state-full` | a rule refused new entities because its state was full | HIGH | once per hour |

Engine defaults (`Settings.defaults()`): dedup window 1 h; 50 new alerts per rule per hour (200 for CRITICAL rules); 50,000 open windows; 20,000 keys per counting rule; read chunks of 500; 1,000,000 events per poll.

## Design decisions and why

1. **One AEAD per record, sequence and store id as associated data.** Encrypting records one by one keeps the file append-only (nothing earlier is ever rewritten) and lets a reader find damage at the exact record. Binding the sequence stops a frame being moved or replayed; binding a random store id stops frames being spliced in from another store file that uses the same key. Random 96-bit nonces are safe up to 2^32 records per key (SP 800-38D 8.2.2); the store caps a file at 2^31 records.
2. **The store enforces the chain on write.** It accepts only sequence + 1 linked to the previous MAC, so a buggy or hostile caller can never leave a gap or a fork in the file, and a store that found damage refuses to append after it (fail closed: `AuditLog.append` then throws, and every enforcement point already turns an audit failure into a deny).
3. **Damage is loud, not an end of file.** Reading past damage throws instead of returning an empty batch. A reader that took the end of the good records for the end of the trail would silently lose everything after the damage. `DetectionEngine` turns the exception into `audit-chain-break`.
4. **Escape names as well as values, per format.** JSON uses the project's `JsonWriter`. CEF cannot escape extension keys at all, so payload names become `dwf<name>` when they are 1 to 28 letters and digits and `dwh<24 hex of SHA-256>` otherwise: never a standard key (`suser` in a payload is `dwfsuser`), and never two names on one key. Syslog names follow the same scheme (`f…` / `h…`, at most 32 characters). Control, line-separator and bidi characters become the visible text `\\uXXXX` in CEF and syslog. Values are cut at 2,048 characters and lines at about 32 KiB, with **short values first**, so a huge attacker-chosen value can push out only other huge values, never the subject, address or outcome. The JSON line is the lossless archive form.
5. **Detection owns its cursor.** The engine takes the audit key and builds the keyed cursor itself. A caller cannot hand it an unkeyed cursor by mistake, so every event a rule sees is proven to be Dwarpal's.
6. **Checking the anchor when the reader is exactly on it.** `AuditCursor.checkAgainst` can only compare at or before the read position. The engine caps each read so that it stops exactly at the anchored sequence, compares there, and only then reads on. A trail rewritten at the anchor and extended beyond it is still caught (`aTrailRewrittenAtTheAnchorIsCaughtEvenIfItGoesOnBeyondIt`).
7. **Deterministic by construction.** Alert times are audit times, ids are `al-<rule>-<sequence>`, windows open and close on audit time, fields are exported in a fixed order. The same trail read in chunks of 500 or of 7 gives identical alerts (`theSameTrailGivesTheSameAlertsWhateverTheBatchSize`).
8. **Deduplication: raise at once, then one roll-up.** The first hit of a rule for an entity is raised immediately (a honeytoken hit must not wait an hour). Repeats inside the window are counted and raised once, when the window closes (or on `flush`), as `al-<rule>-<first>-x<count>` with that count and up to 100 of their sequence numbers. That gives one alert per entity per window plus at most one roll-up.
9. **Throttle per rule, with a separate higher cap for CRITICAL rules.** Noise from a busy rule cannot use up the cap of a rare, important one. CRITICAL rules are capped too (R-A3); only the trail's own two alerts are uncapped, and they fire at most once.
10. **Refuse rather than forget.** When a counting rule's state is full, it first drops keys idle for a whole window (access order, amortised constant time), then refuses new keys and counts them. Forgetting a live key would let an attacker flood the table to reset a counter that is about to fire. The refusals raise `detection-state-full`, so evasion by flooding is visible.
11. **No silent loss of alerts.** An alert the sink refuses (or a sink that throws) is queued and offered first on the next poll; while anything is waiting, no further events are read (back-pressure). The queue is bounded by the open-window limit plus a margin; `lost` counts anything beyond, and has stayed 0 in every test.
12. **Rules read only what Dwarpal's code writes.** Types, policy ids, outcomes and ids, plus two fixed texts (the PA's token-theft reason and the `factors` rendering). The factor is found by a plain index search, not a regular expression (FindSecBugs flagged the first version as ReDoS-prone), and only at a factor boundary (`[` or `, `), so text inside another factor's evidence cannot pose as one. Ids that fail `Validate.id` (only possible in a record Dwarpal did not write) become `invalid-<hash>` instead of being dropped, so they cannot be used to hide.
13. **Alert summaries carry ids and counts only.** They never copy free text from a payload, so they cannot carry secrets or forge lines (the `Alert` record sanitises them as well).

## Threats and mitigations (STRIDE)

| # | STRIDE | Threat | Mitigation in code | Test |
|---|---|---|---|---|
| A1 | Info disclosure | A stolen disk, backup or copied store file reveals the audit trail (who accessed what, from where) | AES-256-GCM per record; the key is passed in and never written; no plaintext or key bytes in the file | `theFileHoldsNeitherPlaintextNorTheKey`, `theWrongKeyReadsNothing` |
| A2 | Tampering | Bit flips, swapped records, a replayed record, a frame spliced from another store, a changed header | GCM tag over each record with sequence and store id as associated data; detected on open and on every read; writes refused afterwards | `aFlippedBitIsDetectedAndEarlierRecordsStayReadable`, `swappedRecordsAreDetected`, `aReplayedRecordIsDetected`, `aChangedStoreIdBreaksEveryRecord`, `aFileChangedAfterOpeningIsCaughtOnRead`, `aFrameAppendedWithoutTheKeyIsDamageAndAChainBreak` |
| A3 | Tampering / repudiation | A trail cut back at a record boundary (invisible to the store and to the chain) | `HeadAnchor` in a separate place; the engine compares at the anchor; stale, rolled-back, rewritten or removed anchors are refused | `aTruncationAtAFrameBoundaryNeedsTheAnchor`, `aTruncatedTrailDisagreesWithItsAnchor`, `aRemovedOrRolledBackAnchorIsTamperingOnceOneExisted`, `rA1_aRestoredOldAnchorIsStaleAndStopsDetection` |
| A4 | Tampering | A caller (or bug) writes a gap or a fork into the store | Only sequence + 1 linked to the previous MAC is accepted | `onlyTheNextRecordOfTheChainIsAccepted` |
| A5 | Denial of service | Huge records or a corrupt length field exhaust memory | Records at most 1 MiB, refused before writing; frame length bounds-checked before allocating; batches capped | `oversizedRecordsAreRefusedBeforeAnythingIsWritten`, `aFrameLengthOutOfBoundsIsDamageNotAHugeAllocation`, `batchesAreCappedLikeEverySource` |
| A6 | Tampering | Two writers on one file interleave frames | File lock on a byte past the end (readers never blocked on Windows) | `aSecondWriterOnTheSameFileIsRefused` |
| A7 | Spoofing / tampering | A field value or name forges another field or another event in the SIEM (CEF `\|` `=`, syslog `]` `"`, new lines, bidi) | Per-format escaping of names and values; names mapped to safe, distinct keys; one event per line | `cefCannotBeForged`, `cefHeaderFieldsEscapePipesAndBackslashes`, `syslogCannotBeForged`, `jsonLinesAreLosslessAndOneLine`, `namesMapToDistinctSafeKeys` |
| A8 | Denial of service / repudiation | One huge value pushes the subject or address out of a size-capped SIEM line | Values cut at 2,048, lines at about 32 KiB, short fields first, no split surrogate pairs | `aHugeValueCannotPushOutTheSubject`, `cuttingNeverSplitsASurrogatePair` |
| A9 | Spoofing | Detection fed forged or edited records raises alerts against innocent people, or misses real ones | Keyed cursor built by the engine; a break raises one CRITICAL alert and stops for good | `aRecordForgedWithAnotherKeyIsNeverDetectedOn`, `aChainBreakRaisesOneCriticalAlertAndStopsForGood`, `aSourceThatThrowsIsABreakNotAnEnd` |
| A10 | Denial of service (SOC) | An alert flood drowns the analysts or buries a real CRITICAL alert | Per-entity dedup with roll-up; per-rule hourly caps (separate cap for CRITICAL rules); one `alert-flood` alert | `repeatsFoldIntoOneAlertAndARollUpWithTheirCount`, `aDenyFloodCannotBuryABreakGlassAlert`, `rA3_honeytokenFloodsAreCappedWithOneCriticalFloodAlert` |
| A11 | Denial of service / evasion | Detection state flooded with invented entities, so the real attacker is not tracked, or memory runs out | Bounded state; idle keys dropped, live keys never forgotten; refusals counted and alerted | `floodingDetectionStateRaisesStateFull`, `windowCounterIsBounded`, `boundedUnderAMillionEvents` |
| A12 | Elevation (SOC as a weapon) | Junk requests in the CEO's name make detection point at the CEO, so a playbook locks the CEO out | `deny-storm-subject` names the person as target plus the attacking addresses, and says it is not evidence against them; request 4 to part B | `junkInSomeonesNameNamesTheAttackingAddresses` |
| A13 | Evasion | An attacker resets a counting rule between attempts (MFA fatigue) | Only an ALLOW ends a step-up run | `rA2_aDenyBetweenPushesDoesNotResetMfaFatigue`, `mfaFatigueNeedsFivePushesWithoutAnAllow` |
| A14 | Repudiation / info loss | Alerts lost when the case book is full or down | Refused alerts kept and retried; reading stops while any wait; `lost` counted | `alertsTheSinkRefusesAreKeptAndNothingMoreIsReadUntilItAccepts`, `aSinkThatThrowsIsTreatedAsRefusing` |
| A15 | Tampering | A factor name forged inside free text makes a decision look like impossible travel | Index search only at a factor boundary; number length capped; NaN and non-positive refused; no ReDoS-prone regex | `onlyARealPositiveTravelFactorCounts` |
| A16 | Info disclosure | Alerts or exceptions carry secrets or payload text | Summaries carry ids and counts only; damage messages name record numbers only; invalid ids hashed | `oddIdsInARecordStillCountAndNeverReachAnAlertRaw` |

## Red-team findings

Each was first a working probe against the code as written (all three probes passed, showing the breach), then fixed, and is kept as a regression test in `RedTeamTest`.

| # | STRIDE | Breach (before the fix) | Root cause | Fix | Test |
|---|---|---|---|---|---|
| R-A1 | Tampering | An attacker who can write the store and the anchor directory cut the store back to record 5 and put back a copy of the anchor file from record 5. After a restart, the trail agreed with "its" anchor: five records (all `BREAK_GLASS_USED`) gone without trace | A new `HeadAnchor` instance has no memory of later anchors, and an anchor carried no notion of age | Every write renews the anchor's time (a heartbeat, even when the head is unchanged); `readFresh(maxAge)` refuses an anchor older than the schedule allows (or dated in the future), and detection treats that as `audit-anchor-mismatch` | `rA1_aRestoredOldAnchorIsStaleAndStopsDetection`, `rA1_aLiveAnchorStaysFreshOnAQuietTrail` |
| R-A2 | Evasion | 40 MFA pushes to the CEO in 15 minutes raised no alert: the attacker sent one deliberately bad request (from Tor, so DENY) after every fourth push | The fatigue rule reset its count on any decision that was not a STEP_UP, including a DENY the attacker could cause at will | Only an ALLOW (a successful decision for that person) ends a run | `rA2_aDenyBetweenPushesDoesNotResetMfaFatigue` |
| R-A3 | Denial of service (SOC) | Someone who knows a honeytoken's id sent 2,000 requests with invented device ids: 2,000 CRITICAL alerts, none throttled (alert fatigue, and part B's playbooks run per alert) | CRITICAL alerts were exempt from throttling, and the honeytoken dedup key includes the device | CRITICAL rules get their own cap (200 per rule per hour), then one CRITICAL `alert-flood` alert; the rest are counted | `rA3_honeytokenFloodsAreCappedWithOneCriticalFloodAlert` |

Also found and fixed during the pass (hardening, no working breach): FindSecBugs flagged the first impossible-travel regular expression as ReDoS-prone, now a plain index search; the anchor's temporary file is now created fresh with `CREATE_NEW` so a planted file or link is never written through; value cutting no longer splits a surrogate pair; syslog lines now carry the full event type (MSGID is cut at 32 characters).

Attacks on the SOC that held without a fix: a flood of one rule cannot bury a break-glass alert (`aDenyFloodCannotBuryABreakGlassAlert`); flooding rule state is visible (`floodingDetectionStateRaisesStateFull`); a frame forged with another store's key and appended to the file is damage plus one chain-break alert, never a break-glass alert (`aFrameAppendedWithoutTheKeyIsDamageAndAChainBreak`); junk in the CEO's name names the attacking addresses (`junkInSomeonesNameNamesTheAttackingAddresses`).

## Requests to integration

1. **`AuditLog` cannot continue an existing trail.** It always starts at sequence 0 and the genesis MAC, so after a restart over an existing `EncryptedAuditStore` its first write (sequence 1) is refused (correctly, fail closed) and every decision becomes a deny. Please add a way to resume from a stored head, for example `AuditLog(key, sink, AuditLog.Head resumeFrom)`, used as `new AuditLog(key, store, store.head())`. Until then the store works for one process lifetime per file.
2. **Structured fields instead of free text.** Two rules match texts written by other packages: `SESSION_REVOKED` reason "possible token theft" (`PolicyAdministrator`) and the `factors` rendering of `RiskFactor` (`AuditedDecisionPoint`). Please add `cause=token-theft` to that revocation, and to `ACCESS_DECISION` a field listing the positive factor names (for example `signals=impossible-travel,network-novelty`). The rules will switch to them, and a change of wording can then no longer silently disable a rule.
3. **`AuditCursor.checkAgainst` and anchors behind the read position.** It cannot check an anchor that the reader has already passed. `DetectionEngine` works around this by stopping each read exactly at the anchored sequence. A cursor that remembers the MAC at a requested sequence would let every reader check old anchors.
4. **Part B, playbooks on `deny-storm-subject` and `mfa-fatigue`.** These alerts name the person who is being attacked. Anyone can send requests in someone's name, so a playbook that denies the SUBJECT of these alerts lets an attacker lock out the CEO by sending junk. Act on the IP entities (deny the address), or watch or force MFA on the person, never deny them on these rules alone. Worth a cross-part red-team test at integration.
5. **Three keys, kept apart.** Audit HMAC key, store AES-256 key and anchor HMAC key are separate, and none of them is ever written next to the data. The runtime or demo launcher should load them from separate environment secrets, and keep the anchor file on another volume or account than the store. On Windows the store file has no POSIX permissions; the installer should set an ACL so only the service account can read it.
6. **Wiring.** `HeadAnchor.schedule(executor, store::head, Duration.ofMinutes(1))` and, for detection, `() -> Optional.of(anchor.readFresh(Duration.ofMinutes(3)))` as the anchor supplier. `EncryptedAuditStore.Durability.SYNC_EVERY_RECORD` in production. `DetectionEngine.poll()` on a schedule, its `checkpoint()` saved somewhere trusted for `resume`.
7. **Threat model.** Please add A1 to A16 and R-A1 to R-A3 above to `docs/threat-model.md`. Residual risks to list: detection windows start from zero after a restart (state is in memory); thresholds are assumptions until part C calibrates them; a rule's hourly cap means a determined flood hides further alerts of the *same* rule in that hour (they are counted and the flood itself is alerted); an attacker who can write both the store and the anchor and also stop the anchor schedule for less than `maxAge` can hide at most the records written since the last anchor.
8. **No shared file changes needed**: no new dependency, no SpotBugs suppression, no `pom.xml` change.
